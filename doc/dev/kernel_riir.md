Lean kernel + runtime RIIR (Rust)
===============================

Scope
-----
- Rewrite the Lean 4 kernel and runtime from C++ to Rust.
- Cover all non-autogenerated C++ in `src/kernel` and `src/runtime`.
- Preserve the C ABI and FFI surface (keep `lean/lean.h` compatible).
- Maintain correctness by cross-checking against the C++ kernel until parity.

Primary goals
-------------
- Correctness: bit-for-bit compatible semantics with the existing kernel.
- Performance: improve throughput and memory behavior from day one.
- Parallelism: enable safe, internal parallel passes where it helps.
- Zero-copy: minimize allocation and copying along kernel hot paths.
- FFI stability: no breaking changes to the C API or runtime object model.

Non-goals (for early phases)
----------------------------
- Changing the surface language or elaborator behavior.
- Replacing all runtime C APIs with Rust-only APIs.
- Removing the existing C++ kernel immediately (dual-kernel phase first).

Data structure direction (kernel)
---------------------------------
- Expr/Level representation:
  - Immutable DAG nodes, hash-consed by (kind, fields).
  - Interned strings/names with stable indices for fast equality.
  - Inline small tags in pointer-aligned headers to reduce branches.
- Allocation:
  - Arena allocation for nodes with epoch-based reclamation.
  - Intrusive refcount for long-lived DAGs where arena lifetime is too coarse.
  - Zero-copy slices for binder lists and local context views.
- Memoization:
  - Per-thread caches for normalization/type-checking.
  - Sharded global caches with contention-aware hashing.
- Parallelism:
  - Parallel environment replay for independent decls.
  - Work-stealing evaluation for large modules (optional flag).

Data structure direction (runtime)
----------------------------------
- Preserve `lean_object` layout but implement in Rust.
- Lean object header: 64-bit packed header with refcount + tag + flags.
- Replace ad-hoc per-type allocation with allocator classes:
  - Small-object slab allocator for common tags.
  - Bump arenas for short-lived runtime values.
- ByteSlice/Name/String:
  - Interned string table with copy-on-write and zero-copy slicing.
  - Stable hashes to reduce recompute in hash tables.

FFI and ABI plan
----------------
- Keep `stage0/src/include/lean/lean.h` as the source of truth for ABI.
- Rust types use `#[repr(C)]` and mirror the C structs exactly.
- Extern functions expose the same symbols; C++ becomes a thin shim.
- C ABI is preserved so existing C/C++ extensions continue to work.

Cross-checking and external kernels
-----------------------------------
- Use `lean4checker` to replay oleans and detect environment hacks.
- Use `lean4lean` as a secondary kernel implementation for cross-checking.
- Maintain a dual-kernel mode that compares Rust vs C++ results:
  - If divergence, report both traces and reduce to a minimal repro.

Phased migration plan
---------------------
1. Scaffolding:
   - Add Rust crates for kernel/runtime and CMake wiring.
   - Provide FFI shims with no behavior change.
2. Kernel core:
   - Port `level`, `expr`, `environment`, `declaration`.
   - Preserve exact hashing and equality semantics.
3. Type checker:
   - Port normalization, definitional equality, inductives, quot.
   - Keep a side-by-side checker until parity is validated.
4. Runtime:
   - Port object layout, allocator, io, threading, and libuv bindings.
   - Preserve the C ABI and verify with existing runtime tests.
5. Optimization:
   - Profile-driven tuning and zero-copy improvements.
   - Introduce optional parallel passes behind flags.

Debugging and bisecting
-----------------------
- Keep a debug-only trace mode that logs the kernel decision path.
- Export minimized counterexamples when kernels diverge.
- Add a knob to toggle Rust vs C++ kernels per module.

Risks
-----
- ABI drift across platforms if header layout changes.
- Performance regressions from allocation strategy or refcounts.
- Subtle differences in definitional equality and reduction.

Success metrics
---------------
- `lean4checker` and `lean4lean` agree on core and stdlib.
- Kernel-heavy benchmarks (qsort, rbmap, parser) are no slower.
- Memory footprint stays within 10 percent of baseline (ideally better).
